# Publication Route Memory Knowledge

Owner: MedAutoScience
Knowledge role: executable memory rules for reusable publication-route experience
Machine boundary: OPL resolves authorized knowledge sources and binds selected bytes to frozen Stage context. MAS and the appropriate knowledge owner retain body acceptance, rejection, and writeback authority; Framework write operations only apply exact accepted updates.

## What Memory Can Contain

Publication-route memory may hold:

- route patterns that previously worked or failed for similar study lines.
- journal-neighbor expectations, reader risks, and reviewer pressure patterns.
- figure/table/story patterns tied to evidence refs.
- common source, provenance, methodology, citation, display, and artifact blockers.
- stop-loss rules, claim downgrade examples, and route-back lessons.
- accepted or rejected writeback records with router receipts.

## How To Use Memory

- Read memory as advisory prior experience, not as current evidence.
- Use memory to generate candidate routes, anticipate reviewer risk, choose robustness checks, and avoid repeated failed paths.
- Link memory use to current refs: study charter, evidence ledger, source readiness, manuscript refs, and controller decisions.
- Preserve memory-derived warnings in receipts so later stages can see why a shortcut was avoided.
- When memory suggests a new claim boundary, route to decision or human gate rather than applying it locally.
- Separate product methods, owner/team policies, disease-topic lessons and Study-specific decisions. Scope does not prescribe a physical directory: an existing Obsidian library and local Markdown use the same source binding, and each knowledge object has one canonical body.
- Source edits, expiry, revoked access and supersession remove affected entries and derived summaries from current use until reviewed. Optional experience can be omitted; missing required evidence or policy blocks the dependent judgment.

## Writeback Rules

A memory writeback proposal must include:

- `source_refs`: source stage, study evidence, failed-path and review receipts.
- `target_scope: {kind, id}`: the product, owner, topic or project that owns the accepted lesson.
- `content_kind`: mechanism, policy, state or decision, independently of scope.
- `proposed_rule_or_mechanism`: the proposed text and its clinical, route and failure boundaries.
- `evidence_class`: the supporting evidence maturity and observation context.
- `review_requirement`: the actual knowledge owner and acceptance needed for this update.

The relevant MAS reviewer/auditor, route authority or user/team knowledge owner accepts or rejects the proposal within its own scope. Programs and materializers may validate shape/currentness and apply the exact accepted bytes to the canonical source, with version checks and readback; they cannot decide memory acceptance. A concurrent edit requires reconciliation. A single Study result never automatically becomes a cross-study or product rule.

## Forbidden Uses

- Do not use memory as a substitute for literature search, source readiness, evidence, citation integrity, AI reviewer quality, or publication verdict.
- Do not copy memory body into current study truth without an accept/reject record.
- Do not treat memory locator presence as readiness.
- OPL may bind selected body bytes as scoped Stage context; semantic acceptance remains with MAS.

## Route Impact

Memory can justify route-back, stop-loss, robustness checks, manuscript caveats, or reviewer concerns. It cannot by itself advance a stage. Every memory-driven action must still cite current MAS refs and end in an owner receipt, typed blocker, route-back, or human gate.
